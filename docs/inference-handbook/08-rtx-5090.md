# 8. RTX 5090 Blackwell lab

[Previous](07-engineering-method.md) · [Index](README.md) · [Next](09-engine-comparison.md)

**External:** NVIDIA specifies RTX 5090 as Blackwell with 32 GB GDDR7, 512-bit
interface, 21,760 CUDA cores and 5th-generation Tensor Cores; NVIDIA’s launch
article gives 1,792 GB/s memory bandwidth. Sources: [product
specification](https://www.nvidia.com/en-us/geforce/graphics-cards/50-series/rtx-5090/)
and [architecture announcement](https://www.nvidia.com/en-us/geforce/news/rtx-50-series-graphics-cards-gpu-laptop-announcements/).

Consumer Blackwell uses compute capability `sm_120`. Do not assume a binary for
datacenter Blackwell `sm_100` runs optimally—or at all. Build a native `sm_120`
cubin with a toolkit that supports it and inspect the produced fatbinary. CUDA
12.8 introduced Blackwell support; later toolkit/driver combinations may fix
library behavior, so record exact versions. The [CUDA Blackwell tuning
guide](https://docs.nvidia.com/cuda/blackwell-tuning-guide/) and [CUDA release
notes](https://docs.nvidia.com/cuda/cuda-toolkit-release-notes/) are the primary
compatibility references.

## What FP4 changes

FP4 Tensor Cores can raise matrix throughput and halve nominal value bytes versus
FP8, but require supported MMA shapes, scale formats, layout, activation
conversion, and sufficient matrix work. Decode at batch one may remain bandwidth
or launch limited. DwarfStar’s CUDA comment near the MXFP4 MoE dispatch states
that Blackwell MMQ uses FP4 MMA while decode uses the MMVQ path; treat actual
5090 behavior as **Proposed**, because this checkout has no local 5090 result.

## Memory budgets

**Estimated Qwen BF16 lower bound:** `27e9 * 2 = 54 GB` decimal (50.3 GiB) for
language weights alone. It cannot fit 32 GB before vision weights, MTP, KV/state,
workspace, allocator and CUDA overhead.

**Estimated 4-bit lower bound:** `27e9 * 0.5 = 13.5 GB` decimal (12.6 GiB).
Real quant blocks include scales; embeddings/output, sensitive recurrent paths,
vision and MTP may remain BF16/FP16. Reserve, illustratively, 16–22 GiB for
weights/repacked copies, 1–4 GiB for CUDA/workspace, and leave the remainder for
state and safety. These are scenario bounds, not a claim that a particular file
fits. Measure its actual tensor inventory.

For Qwen full-attention layers only, an unquantized BF16 KV estimate is:

```text
16 layers * 2(K,V) * 4 KV heads * 256 dims * 2 bytes * context
= 65,536 bytes/token
= 16 GiB at 262,144 tokens
```

The 48 DeltaNet layers use fixed recurrent/conv state rather than a token-growing
standard KV cache, but their exact implementation state and batching copies must
be added. At 32K tokens, the formula gives 2 GiB for full-attention KV. Vision
tokens also consume sequence/state budget.

**Estimated DeepSeek:** Flash Q2 is described by this repository for 96/128 GB
RAM systems. Resident single-5090 inference is outside its intended budget;
streaming is a research experiment, not a promised usable configuration.

## Experiment card

1. Build native `sm_120`; save compiler/toolkit/driver output.
2. Inventory file tensors and runtime allocations before loading.
3. Run correctness fixtures with graphs and FP4 paths disabled/enabled.
4. Nsight Systems: TTFT/ITL, launch gaps, overlap, PCIe/storage.
5. Nsight Compute: selected MMVQ/MMQ kernels, DRAM throughput, Tensor Core
   utilization, registers, occupancy, spills, stall reasons.
6. Sweep prompt 128/2K/8K, output 256, batch 1/2/4/8, context frontier, and
   quant format. Alternate A/B order and publish raw data.

Expected observations: prefill benefits more from MMQ/FP4; decode approaches a
weight-bandwidth/launch floor; batching improves aggregate throughput while
raising queueing and state memory. Any different result is valuable—do not tune
the report to the expectation.
